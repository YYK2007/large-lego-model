# Large Lego Model: project instructions

Read `docs/OBJECTIVE.md`, `docs/STAGES.md`, and `docs/VERIFICATION.md` before changing product behavior. Keep the supplied Karpathy-style principles: explicit assumptions, minimum necessary implementation, surgical changes, and verifiable outcomes.

## Product requirements

**Current priority: resemblance to the real subject.** For named or recognizable real-world objects, retrieve existing reference photographs, verify the subject, feed actual image pixels into planning, and retain source/credit links. Compare the generated geometry with those references for silhouette, proportions, materials/colors, and distinctive features before calling it a successful match. Geometry validity alone is insufficient. Expand the usable scale and real-part catalog where they force crude approximations; preserve exact parts, connections, inventory, and matching exports. More pieces alone are not evidence of likeness. Use the Morehead-Patterson Bell Tower as the first visible before/after acceptance case.

- Call the architecture **Large Lego Model**. The product name is provisional.
- **Use a calm, playful building-assistant identity within the Frutiger Aero / Y2K brief.** Windows XP is an influence, but the literal desktop-window theme was rejected. Use light sky colors, greenery, selective glossy controls, clear spacing, and dimensional model lighting across the website, iMessage media, and manual. Keep actual part colors faithful and diagrams readable.
- Study actual **LEGO Builder** screens and official demonstrations before deciding assembly UX. Record sources and what was observed. Prioritize part callouts, precise placement, orientation, camera behavior, subassemblies, and clear progress. Do not claim to have operated the mobile app when only a video or screenshot was inspected.
- Generate genuinely three-dimensional and increasingly complex builds. A wide plinth underneath a thin relief is not sufficient. Inspect multiple sides, depth, internal structure when relevant, and subassembly needs. Flat designs are appropriate only when requested.
- **No application-imposed piece-count ceiling or default small-piece budget.** Prioritize interesting, complex builds through meaningful structure, openings, interiors, repeated details, and connected sections appropriate to the prompt. Keep explicit user-requested budgets and owned-inventory limits. Verify larger models with geometry, performance, multi-angle appearance, and assembly checks; extra pieces alone do not establish quality.
- **Support more than rectangular bricks.** Expand the real-part catalog in verified stages: plates, tiles, slopes, curves and wedges, then suitable hinges, wheels, brackets and connectors. Each released family needs accurate geometry, legal connections/orientations, collision checks, exact inventory/BOM accounting, and understandable assembly steps. The current implementation has 36 real part types and 13 colors, with verified part/color combinations; this is an increment, not the finished goal. Do not substitute decorative meshes for usable parts or claim unimplemented families work.
- All previews, animations, native 3D files, BOMs, allocations, and instructions come from the same validated brick model. Never generate illustrative media that invents a different set.
- Keep the direct **Download 3D (.usdz)** action on the build page. Capture the clicked revision before exporting, show failures clearly, and preserve it if the user switches models during preparation. Verify the archive against the exact placements; phone viewing and iMessage delivery require separate device tests.
- Distinguish geometric checks, physical simulation, real hand-building, and live account/device tests. Do not equate connected bricks with mechanically proven stability.
- For iMessage, prefer native user-controlled viewing with a verified fallback. A looping animation is not interactive rotation. Test actual phone behavior before claiming it works.
- Use Gemini in the main multimodal flow and Photon Spectrum for iMessage. ElevenLabs voice notes remain a later stage unless explicitly promoted.
- Make progress reviewable through local checkpoints, tests, documentation, feature-branch commits, and a draft PR. Avoid inflated claims, generic marketing copy, and unnecessary features.
- Keep credentials and user runtime data out of Git. Never print secret values in logs or reports.
- When user input or account setup is needed, provide concrete numbered steps, direct setup links, the exact local fields to fill, and a way to verify completion. Keep secrets out of chat.
- In the website, manual, and iMessage flow, provide exact part/color/quantity requirements, source-set allocations for owned pieces, and useful catalog/set links for shortages. Distinguish a catalog link from verified current price, availability, or a purchase. Never imply the user owns a set they have not confirmed.

## Validation

Checkpoint 05 is in progress, not complete. The working catalog includes rectangular bricks/plates, tiles, two upright slopes, round 1×1 parts and a small cone within a 96×96-stud, 384-plate-height workspace. Ordinary upright stud connections are supported; hinge, bar/hole, sideways and physical load behavior remain unimplemented. Checkpoint 06 adds curved profiles/open shell sectors, plate-course tiling and bounded local repair. A fresh 5,910-piece Taj Mahal reached review, but the critic marked likeness as needing refinement. Organic attempts remain unreliable. Hanging pieces require a checked assembly sequence and matching instructions before allowing connections from above; do not remove the bottom-support gate by itself.

Run relevant tests and `npm run build` after meaningful changes. Inspect the running desktop/mobile UI and generated manual pages; code passing a test does not establish visual quality. Keep `docs/VERIFICATION.md` current and preserve remaining live-test requirements.
